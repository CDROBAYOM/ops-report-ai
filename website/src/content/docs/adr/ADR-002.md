# ADR-002: Ingesta desde fuentes heterogéneas con adaptador tolerante

## Contexto y problema

El archivo fuente de CoopNorte (exportación de SisCredito v2.1) presenta tres problemas técnicos documentados en los fixtures de prueba:

- **Nombres de columna inconsistentes:** el mismo campo llega con nombres distintos dependiendo de quién exportó (`Valor_Mora`, `valor mora`, `MORA`, `Valor_Cartera_Vencida`).
- **Formatos de fecha mezclados:** en el mismo archivo coexisten `dd/mm/yyyy` y `mm-dd-yyyy` sin patrón predecible.
- **Registros duplicados y celdas vacías:** un crédito puede aparecer más de una vez; campos obligatorios como `Saldo_Vigente` pueden llegar vacíos.

El sistema fuente es legacy y no está bajo nuestro control. Si no se decide cómo manejar esta variabilidad, el sistema producirá reportes con datos en estado incierto — o fallará silenciosamente.

## Drivers de decisión

- **Certeza del dato:** nunca producir un reporte con datos en estado incierto; detenerse y alertar ante lo desconocido.
- **Trazabilidad:** cada archivo procesado debe dejar registro de qué se limpió y qué se detuvo.
- **Tolerancia conocida, no permisividad:** el sistema tolera variabilidad documentada; detiene lo que no puede resolver de forma determinística.
- **Separación de responsabilidades:** la detección y validación son determinísticas; la normalización de fechas ambiguas es el único caso que puede requerir IA (ver ADR-003).

## Opciones consideradas

1. **Adaptador en dos fases: mapeo de aliases + validación antes de normalización** (opción elegida)
2. Asumir nombres de columna fijos y fallar si cambian
3. Usar IA para detectar las columnas correctas automáticamente
4. Rechazar cualquier archivo que no cumpla exactamente el formato esperado

## Decisión

Se decide la **opción 1**. El adaptador opera en dos fases secuenciales con responsabilidades estrictamente separadas. Si cualquier validación falla, el proceso se detiene y se genera una `AlertaOperativa(anomalia_dato)` — nunca se procesa un archivo con datos en estado incierto.

**Fase 1 — Detección y mapeo de columnas:** el adaptador mantiene un mapa de aliases conocidos por campo del dominio. Si ningún alias coincide, genera una alerta y detiene el proceso.

**Fase 2 — Validación antes de normalización:** verifica columnas requeridas, elimina duplicados (registrándolos), limpia valores monetarios, y detecta campos obligatorios vacíos.

## Comparación de opciones

| Opción | A favor | En contra |
|---|---|---|
| 1. Adaptador tolerante con aliases | Tolera variabilidad conocida; errores trazables; mapa de aliases documenta la realidad del sistema fuente | El mapa debe mantenerse cuando aparece un nuevo formato |
| 2. Formato fijo | Simple de implementar | El sistema fuente es legacy e inestable; falla en producción con cada nueva exportación |
| 3. IA detecta columnas | Sin mantenimiento del mapa | Introduce incertidumbre donde la solución puede ser determinística; un mapeo incorrecto afecta el índice de mora |
| 4. Rechazar sin formato exacto | Máxima seguridad | CoopNorte no puede estandarizar exportaciones en el corto plazo; el sistema sería inoperable |

## Flujo del adaptador

```
Recibir archivo Excel
        ↓
Detectar columnas → ¿todas presentes?
   NO  → AlertaOperativa(anomalia_dato) → fin
   SÍ  ↓
Eliminar duplicados → registrar en log
        ↓
Validar campos obligatorios → ¿alguno vacío?
   SÍ  → AlertaOperativa(anomalia_dato) → fin
   NO  ↓
Limpiar valores monetarios
        ↓
Pasar a servicio de normalización (ADR-003)
        ↓
Retornar datos listos para el caso de uso
```

## Consecuencias

**Positivas**

- El proceso nunca produce un reporte con datos en estado incierto.
- El mapa de aliases es un artefacto vivo que documenta la variabilidad real del sistema fuente.
- Los errores son trazables: cada archivo procesado deja registro de qué se limpió y qué se detuvo.

**Negativas y mitigación**

| Consecuencia negativa | Mitigación |
|---|---|
| El mapa de aliases debe mantenerse cuando aparece un nuevo formato | Cada nuevo alias requiere una exportación real documentada — no suposiciones técnicas |
| Detener el proceso ante campos vacíos puede generar falsas alarmas si un campo es realmente opcional | Los campos opcionales deben declararse explícitamente en el mapa; la excepción se documenta cuando ocurre |

## Verificación (fitness function)

- **Regla:** para cada tipo de fuente (CSV, Excel, webhook), existe un test de contrato que verifica que el adaptador produce la entidad de dominio correcta o la `AlertaOperativa` correspondiente ante entradas inválidas.
- **Mecanismo:** suite de pruebas de contrato en `test/integration/ingesta/` ejecutada en CI con fixtures reales de `test/fixtures/`.
- **Efecto:** si un cambio en el adaptador rompe el contrato para algún tipo de fuente, el build falla antes del merge.

## Riesgos y cumplimiento

- **Alias sin documentar:** si se agrega un alias sin fixture real que lo justifique, se introduce suposición técnica no verificable. La revisión del PR debe exigir el fixture correspondiente.
- **Campos opcionales mal declarados:** un campo tratado como obligatorio que en realidad es opcional genera interrupciones innecesarias; la política se revisa en cada `revisar-en`.
