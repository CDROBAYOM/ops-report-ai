# ADR-001: Arquitectura hexagonal (Ports & Adapters) como estructura del sistema

## Contexto y problema

El sistema recibe datos desde fuentes heterogéneas con formatos inconsistentes (Excel con columnas variables, fechas en formatos distintos, registros duplicados) y debe producir dos entidades de dominio bien definidas: `ReporteCartera` y `AlertaOperativa`.

Las fuentes de entrada pueden cambiar en cualquier momento: hoy es un Excel exportado desde SisCredito, mañana puede ser un CSV, una API REST o un webhook. El dominio del negocio —qué es un índice de mora, qué constituye una alerta— no debería cambiar cuando cambia la fuente.

Adicionalmente, el sistema usa IA para asistir en la normalización de datos. Esa dependencia externa tampoco debe contaminar la lógica de negocio.

Si no se decide una estructura explícita, los cambios en las fuentes de entrada afectarán la lógica de negocio — y viceversa.

## Drivers de decisión

- **Estabilidad del dominio:** las reglas de negocio no deben cambiar cuando cambia una fuente de datos.
- **Alcance acotado de la IA:** el servicio de IA no puede acceder directamente al dominio (ver ADR-000).
- **Testabilidad:** las pruebas del dominio no deben depender de archivos reales ni de APIs externas.
- **Legibilidad:** la separación de responsabilidades debe ser evidente para alguien que no escribió el código.

## Opciones consideradas

1. **Arquitectura hexagonal (Ports & Adapters)** (opción elegida)
2. Script lineal: leer Excel → procesar → escribir resultado
3. Arquitectura en capas tradicional (MVC)

## Decisión

Se decide la **opción 1**. El sistema se estructura en tres capas explícitas (Dominio, Aplicación, Infraestructura) con dependencias que fluyen hacia adentro. Los adaptadores de entrada y salida implementan puertos definidos por el dominio; el dominio no conoce ninguna dependencia externa.

## Comparación de opciones

| Opción | A favor | En contra |
|---|---|---|
| 1. Hexagonal | Dominio estable ante cambios en fuentes; IA acotada en infraestructura; tests sin dependencias externas | Más archivos y carpetas; requiere disciplina para no romper fronteras |
| 2. Script lineal | Arranque rápido; sin estructura que aprender | Lógica de negocio mezclada con lectura del Excel; se rompe cuando cambia el formato |
| 3. MVC | Familiar para la mayoría; entrega visible | El controlador termina conociendo detalles de la fuente; sin frontera clara para la IA |

## Estructura de carpetas

```
src/
├── core/
│   ├── domain/
│   │   ├── reporte-cartera.entity.ts
│   │   └── alerta-operativa.entity.ts
│   └── ports/
│       ├── ingesta-cartera.port.ts       ← interfaz de entrada
│       └── reporte-output.port.ts        ← interfaz de salida
├── application/
│   └── use-cases/
│       └── procesar-reporte-cartera.usecase.ts
└── infrastructure/
    ├── adapters/
    │   ├── input/
    │   │   └── excel-cartera.adapter.ts
    │   └── output/
    │       └── reporte-json.adapter.ts
    └── ai/
        └── normalizador-ia.service.ts    ← IA acotada a normalización
```

## Consecuencias

**Positivas**

- Cambiar la fuente de datos no requiere tocar el dominio.
- La IA puede reemplazarse o desactivarse sin afectar las entidades.
- Los tests unitarios del dominio son rápidos y sin dependencias externas.
- La separación de capas hace el código legible para alguien que no lo escribió.

**Negativas y mitigación**

| Consecuencia negativa | Mitigación |
|---|---|
| Más archivos y carpetas que una solución directa | La estructura está justificada: la fuente de datos es inestable por diseño |
| Requiere disciplina para no romper las fronteras entre capas | dependency-cruiser ejecutado en CI bloquea imports prohibidos automáticamente |
| Puede parecer sobreingeniería en un caso simple | Este proyecto existe para demostrar que no lo es cuando el problema lo justifica |

## Verificación (fitness function)

- **Regla:** el módulo `core/domain` no puede importar desde `infrastructure` ni desde paquetes `@nestjs/*`; no existen ciclos de dependencia en ninguna capa.
- **Mecanismo:** `.dependency-cruiser.cjs` con tres reglas ejecutado en el job `architecture` de GitHub Actions.
- **Efecto:** si un import prohibido se introduce, el build falla y no se puede hacer merge a `main`.

## Riesgos y cumplimiento

- **Rotación de equipo:** sin las reglas de dependency-cruiser activas, un desarrollador nuevo puede introducir imports prohibidos sin saberlo. La fitness function mitiga esto automáticamente.
- **Complejidad percibida:** el patrón puede parecer excesivo; el README y este ADR deben ser suficientes para que cualquier contribuidor entienda por qué existe la estructura.
